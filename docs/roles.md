# 角色集 v1（使命 A · 软件开发团队 —— 已定稿冻结）

> ✅ 状态：**已定稿（2026-09-14 · 使命 A 经用户确认）**。角色集不再以草案对待；
> 变更需走三层验证 + 边界集/保留集回归（最小 diff + 可回滚），不推翻本文件。
> 团队 = **5 名成员**：`spec` / `architect` / `dev` / `qa` / `ops`（已注册，见 `agents/`）。

## 设计原则（书中依据）

1. **去中心化：无 Manager**。分工不由中心节点下发；每个成员在收到任务后**自主决定**：
   自己做、请求协作、还是移交（handoff）给更合适的成员。
2. **角色差异 = 权限与工具子集差异**（Ch10：角色规程载体决策表）：
   - 权限级（能否写共享区、能否跑测试、能否发布）→ 独立成员 + Harness 层代码门禁；
   - 风格/知识级（怎么写文档、代码规范）→ 该成员的 Skill（按需加载）。
3. **每次协作必须带「新信息」**（Ch10 第一判据）：`qa` 的审核依赖**执行/测试输出**，
   `spec` 的用户澄清依赖**真实问题**，而不是让成员互相复述同一段文本。
4. **对手握真实证据的成员授予最终验证权**：验证器（测试运行结果）属于机制而非角色。

## 五个初始角色

| 成员 ID | 角色 | 核心能力 | 工具/权限档位 | 订阅 |
|---|---|---|---|---|
| `spec` | 需求澄清与规格 | 澄清问题、写 Spec（目标/非目标/取舍/验收标准）、生成任务单 | 写 `shared/spec/`；不动代码 | `planning` `tasks` |
| `architect` | 架构与接口 | 技术选型、模块/接口划分、数据模型；产出 `ARCHITECTURE.md` | 写 `shared/arch/`；只读代码 | `planning` `design` |
| `dev` | 实现（可多实例） | 编码、测试、自证（跑测试）；按任务拆分 `dev-1..N` | 写 `shared/dev-*/`；可运行沙盒命令 | `tasks` `design` |
| `qa` | 独立验证与审计 | 只读代码与验收标准 → 执行测试/渲染/静态检查 → 出具带证据的评审单 | 只读 `shared/`；可运行验证命令；**不可改被测产物** | `review` `tasks` |
| `ops` | 守门与发布 | 按可验证规则放行/回滚；冲突无法按规则解决时递交**人工仲裁** | 只读 + 最小发布权限 | `gate` `conflicts` |

> `ops` 不是 Manager：它不调度、不拆任务、不决定「谁来做」；它只执行**可验证的守门规则**
> （门禁、发布、回滚）并在规则无法裁决时人工仲裁——对应 Ch10「互相扯皮」的对策。

## 协作主链路（SOP 移交包，MetaGPT 式，但控制流自主）

```
用户/任务 ─→ spec ─(handoff)─→ architect ─(handoff)─→ dev(1..N) ─(review_request)─→ qa
                ▲                  │                          │                        │
                └────── review_result(退回) ←────── review_result(退回) ←──────────────┘
                                    └──(ok)──→ ops 守门 → 交付/发布
```

- 每步移交携带：**goal + constraints + accepted_facts（带来源）+ artifact_refs**。
- 退回（review 不过）是**最常见的协作循环**，且必须简洁：`review_result` 负载带
  `findings[{issue, evidence_ref, severity}]`，接收方据此做**最小修复**再移交（最小 diff + 可回滚）。
- 任何成员可越级请求澄清（如 `qa` → `spec`），无需经过中间人——这是去中心化相对
  管理者模式的核心区别（MetaGPT 未实现、本书视作自然扩展设想）。

## 防「扯皮」的仲裁规则（Ch10 失败模式四对策）

1. 冲突先按可验证规则裁决（谁的产物被破坏 → 谁负责重做；验收标准缺失 → 由 `spec` 补）。
2. 规则裁决不了 → 任何成员发 `error` + 主题 `conflicts`，`ops` 汇总后**转人工裁决**；
   人工裁决期间涉及冲突的写操作全部暂停。
3. 目标互斥（两个成员各自「赢了」）→ 不进入互相取消权限的循环；由 `ops` 按任务优先级冻结一方。

## 使命变更规程（受控动态修改 —— 定稿 ≠ 不可改）

> 原则：**协议层/运行时/审计机制与使命无关**（role 在 Agent Card schema 中只是自由字符串；
> 信封/handoff/锁/轨迹 schema 不含角色枚举——这是 M2 就做的解耦，故换使命零协议改动）。
> 使命 = 四个可替换配置层：`docs/roles.md`（人读）+ `system/state/mission.json`（机器读，audit
> 白名单）+ `agents/*/agent-card.json`（5 张卡）+ 评估任务集（边界/保留/安全）。**安全集 3 探针
> 使命无关，换档后照跑**；边界/保留集按新使命重建或用跨使命中立用例。

**v(N) → v(N+1) 规程**（最小 diff + 可回滚，Ch1 设计模式）：

1. **快照**：归档当前 `roles.md` + `mission.json` + 全部卡片到 `evolution/mission-vN/`
   （即回滚点；只增不改）。
2. **起草 v(N+1)**：改 `roles.md`（角色表/工具档位/订阅/SOP 主链路/仲裁规则）+
   `teamctl mission init --mission <ID> --revision N+1 --roles ...`（新角色白名单）+
   逐卡更新 `role/capabilities/tools/skills/subscriptions`（**由运行时执行**——成员侧对
   `agent-card.json` 只读，见安全集 t-safety-root）。
3. **三层验证**（结果/过程/质量，Ch7/Ch9）：
   - 结果层：`card_role_known` 审计通过（卡角色 ∈ 新白名单）+ 全量测试（协议/成员/审计/演练/并行）；
   - 过程层：在**临时工作区**跑一次新使命的最小任务（如 writer→editor→reviewer 提议-审核）
     记录轨迹/消息/用量；
   - 质量层：diff 仅限四个配置层（roles.md/mission.json/卡片/任务集），协议机制零改动可回滚。
4. **回归**：安全集 3/3（`tools/probe_safety.py all`）+ 审计 exit 0 + 旧用例归档不删。
5. **灰度与发布**：先在沙盒工作区切换、再切真实工作区；由**用户（使命所有者）批准**后生效，
   写入 `docs/PROGRESS.md`。回滚 = 恢复快照（步骤 1）。

> 反例（禁止）：成员自改角色卡（已堵死：写范围除名 + audit `card_role_known`）、
> 运行时绕过程序直接改 mission.json 而不同步 roles.md、把协议写死角色枚举。
